# ARENA3 설계 — 세 학습기를 같은 심판으로 겨루기 (0단계·1단계)

작성 2026-10-27. 상태: **설계안 — 사용자 승인 뒤 `config/arena3_v1.json`으로 잠근다.** 이 문서를 쓰는 동안 SUMO·학습·Colab은 실행하지 않았다. 도착 배치 바꾸기만 맥에서 차량 파일 생성으로 확인했다(2.2절).

## 0. 한 줄 요약

평가 규칙을 먼저 잠그고(0단계), Colab 런타임 3개를 동시에 돌린다(1단계).
- A: 심판 기준선(P0·M4·W4) → B′ 관문 평가
- B: B′로 선택 지점 자료 수집
- C: GPT 학습기 G1

Claude·Gemini 학습기(2단계)는 B의 자료가 나온 뒤 같은 심판으로 겨룬다.

## 1. 무엇을 가리려는가

- **주 질문:** 강화학습 학습기가 같은 차량 조건에서 **M4보다 차량당 지연을 줄이는가.** 좌회전, 장기 대기, 충돌 기준도 함께 지켜야 한다.
- **B′의 역할:** M4를 기본으로 하고 선택 지점마다 SUMO 롤아웃으로 고르는 탐색 제어다. 강화학습이 아니다. 두 가지 질문에 답한다.
  - 지금 행동 범위에 M4 위 여지가 있는가.
  - 학습기에게 줄 교사 자료가 되는가.
- **B′는 비교 기준선이 아니다.** B′는 시뮬레이터 내부 상태와 표본 미래를 쓰므로 학습기보다 정보가 많다. 그래서 B′를 이기는 것은 목표가 아니다.
- **보고 표현:** B′가 P0·M4를 넘으면 "탐색 제어"의 결과로 쓴다. 학습기의 결과와 섞지 않는다.

## 2. 0단계 — 심판 잠금

### 2.1 날짜 나누기

쓸 수 있는 날짜는 학습 13일과 검증 2일, 합계 15일이다. 시험 4일과 새 12일은 이미 다 썼으므로 쓰지 않는다. 15일을 날짜 종류별로 나누고, 해시 순서로 평가 날짜를 골랐다. 정렬 키는 `sha256("ARENA3_SPLIT_20261027|" + 날짜)`이고 결과를 보지 않고 정했다.

| 묶음 | 평가 (7일) | 학습 (8일) |
|---|---|---|
| 평일 | 08-11, 08-19, 08-23, 09-06 | 08-12, 08-22, 09-07, 09-26, 09-28 |
| 주말 | 08-13, 08-20 | 08-14, 10-30 |
| 추석 | 09-11 | 09-09 |

- 세 학습기와 B′ 자료 수집은 **학습 8일만** 쓴다. 평가 7일은 심판만 쓴다.
- 평가 날짜 중 08-11·08-23(이전 개발 평가)과 08-13(이전 확인 평가)은 M4를 고를 때 결과를 본 날짜다. 그래서 이 날짜에서는 M4가 조금 유리할 수 있다. 이 치우침은 학습기에게 불리한 쪽이다.
- 09-28(학습)의 07:30에는 원인을 모르는 접촉 사건이 있었다(184·186절). 학습 중에 이런 사건이 나면 그 에피소드를 버리고 기록한다(N3와 같은 방식, 학습기마다 5번 넘으면 멈춤).

### 2.2 도착 배치 — 환경 파일을 고치지 않고 새로 만든다

- 지금은 (날짜, 15분 시간대)마다 도착 배치가 하나로 고정돼 있다. 난수 42·43은 같은 배치의 반복이었다(207절).
- 실행할 때 `focused_scenario.route_seed`만 바꿔 끼운다. 파일은 그대로다.
- 맥에서 확인한 결과(08-12 07:30, 준비 30분 + 제어 60분 + 꼬리 15분 차량 파일):
  - 원래 함수: 파일 SHA `796f57316662`. 207절의 원시 확인값과 같다.
  - 같은 함수를 끼운 경우: `796f57316662`로 같다. 끼우는 방식이 결과를 바꾸지 않는다.
  - 새 배치(`ARENA3|E1`): `31ad4f4f8fcb`로 달라진다. 차량 수는 10,161대로 같다. 수요 기록이 같고 도착 시각·갈래 배정만 달라지기 때문이다.
  - 환경 지문(pet1, 북쪽 240 m): 바꾸기 전후 모두 `b20888514ea3`.
- 배치 이름은 `E1·E2`(평가), `C1·C2`(승자 확인용, 4단계까지 쓰지 않음), `T<번호>`(학습용)로 둔다.
- 배치 난수는 `sha256("ARENA3|<이름>|<날짜>|<시간대>")`의 앞 4바이트로 정한다.
- SUMO 난수는 배치 난수와 따로, 상황마다 해시로 정한다. FIXED24에서 시간대와 난수가 묶였던 실수를 되풀이하지 않는다.

### 2.3 평가 상황 84개

- 상황 = 평가 날짜 7개 × 시간대 6개(07:30·10:00·12:30·15:00·17:30·21:00) × 도착 배치 2개(E1·E2) = **84개**.
- 수요 자료는 84개 모두 있다(맥에서 확인). 15분 교통량은 409~1,699대다. 추석 07:30이 가장 적다.
- 에피소드 구조는 기존과 같다. 실제 신호 30분 → 정책 제어 60분 → P0 꼬리 900초.
- 평가 대상 차량은 제어 60분 안에 출발 예정인 차다. 정책과 무관하게 정해진다.
- 상황마다 모든 정책이 같은 차량 파일·SUMO 난수·운영 규칙을 쓴다. 잠글 때 상황별 차량 파일 SHA 84개를 `config/arena3_v1.json`에 적고, 실행할 때마다 대조한다.

### 2.4 판정 기준 (실행 전에 고정, 결과를 보고 바꾸지 않음)

**주 지표**
- 정책 X의 M4 대비 이득 = 날짜별 (M4 차량당 지연 − X 차량당 지연)의 평균이다.
- 날짜별 값은 그 날짜 12상황의 차량 가중값이다. 평균을 낼 때는 날짜 7개를 똑같이 센다.
- 차량 가중 전체 평균(이전 공식 방식)도 함께 보고한다.

**통과 조건 (모두 만족해야 통과)**
1. 이득 ≥ +0.3초
2. 날짜 7개에 대한 95% t구간(자유도 6, t = 2.447)의 하한 > 0
3. 이득이 양수인 날짜가 5개 이상
4. 좌회전: 동쪽·남쪽 좌회전 차량 가중 지연이 각각 M4 + 5.0초 이내(WEIGHT1과 같은 허용치)
5. 장기 대기: 지연 300초 초과 차량 수가 M4보다 많지 않을 것
6. 품질
   - 차량 누락·미완료 0, 비용 정산 통과, 정책 행동 오류 0
   - 정책 X에서만 나는 미확인 충돌 0
   - M4·P0에서도 같은 상황·같은 곳에 나는 사건은 '정책 무관 후보'로 따로 적는다. 재현으로 원인을 확인하기 전까지는 통과 판정을 보류한다.

**심판의 감도 확인**
- M4는 P0보다 이전 세 묶음에서 모두 0.8~1.1초 짧았다.
- 같은 기준(이득 하한 > 0)으로 M4 대 P0를 계산해, 하한이 0 이하이면 결과에 '심판 감도 부족'을 표시한다. 판정을 바꾸지는 않는다.

**학습기의 결과**
- 학습 난수 3개로 만든 모델 3개를 모두 평가한다.
- 상황마다 3개 모델의 지연을 평균한 값으로 판정한다. 가장 좋은 모델만 고르지 않는다.

**승자와 확인**
- 통과한 학습기 가운데 주 지표가 가장 큰 하나를 고른다.
- 그 학습기를 새 배치(C1·C2, 같은 7일 × 6시간대 = 84상황)에서 M4·P0와 다시 비교한다. 같은 조건을 만족해야 최종 통과다.
- 셋 중 최고를 고를 때 생기는 운을 걸러내기 위한 단계다. 날짜는 같은 7일이므로 새 날짜 일반화는 아니다.

**기준 정책**
- 비교 기준은 M4로 고정한다.
- W4(4배 고정)는 함께 재지만, 결과를 본 뒤 기준을 W4로 바꾸지 않는다.

### 2.5 예산과 장부

- 계산 한도는 해제됐다(207절). 그래도 학습기 사이의 공정성을 위해 **학습기마다 자기 학습에 쓰는 예산을 60 CPU-시간으로 똑같이** 둔다. 시뮬레이션, 롤아웃, 경사 갱신, 저장을 모두 포함하고 심판 평가는 뺀다.
- B′ 자료는 공용 기반이라 학습기 예산에 넣지 않는다. 어느 학습기든 쓸 수 있다.
- 다만 G1은 B′ 자료 없이 시작하는 순수 RL이고, Claude·Gemini 학습기는 교사 자료를 쓴다. 이 차이는 비교하려는 '학습 방식'의 일부로 보고 결과에 적는다.
- 장부는 런타임마다 따로 둔다. 같은 결과 폴더를 두 런타임이 동시에 쓰지 않는다.

```
MyDrive/FutureTraffic/arena3/
  lock/               잠금 설정과 해시(한 번 쓰고 끝)
  referee/baseline/   런타임 A: P0·M4·W4
  referee/bprime/     런타임 A: B′ 관문 평가
  referee/G1/         런타임 C: 학습이 끝난 뒤 심판 코드로 평가
  bprime_data/        런타임 B: 선택 지점 자료
  G1_train/           런타임 C: 학습
```

### 2.6 세 학습기가 함께 쓰는 규칙

**행동 범위: 가중치 모드 6개**
- WEIGHT1의 5개 (1,1)·(1.5,1)·(1,1.5)·(1.5,1.5)·(2,2)에 W4 (4,4)를 더한다.
- W4를 넣는 이유: 총 지연은 M4와 구분되지 않았지만 좌회전 지연이 21%·11% 낮았다(FIXED24). 좌회전 기준을 지킬 후보다.
- 선택 지점은 6개 모드의 첫 녹색이 둘 이상으로 갈리는 순간이다. 후보는 그 서로 다른 첫 녹색들이다(최대 4개).
- 선택 지점이 아니면 모든 모드가 같은 녹색을 내므로 그대로 실행한다.

**공통 관측 119칸**
- 기존 110칸 + W4의 첫 녹색 표시 4칸 + W4 유효 표시 1칸 + M4 가중치로 계산한 녹색별 비용 차이 4칸.
- 기존 110칸에는 이미 P0 녹색별 비용 차이와 165초 기준 최장 대기가 들어 있다. 새로 더하는 것은 M4 기준 비용뿐이다.
- M4 비용은 선택 지점에서만 계산한다. 계산은 녹색 하나당 P0 계획 한 번 정도다.

**정책 연결 방식**
- 정책은 5초마다 공통 스냅숏을 받아 녹색 하나를 돌려준다.
- 운영 규칙(SignalConstraints)이 마지막에 고친다.
- 심판은 모든 정책을 같은 코드로 돌리고 같은 지표를 계산한다. 지표는 기존 `explore_weight_episode`의 정확 정산을 재사용한다.

## 3. 1단계 — 런타임 3개를 동시에

### 런타임 A — 심판

1. **재현 점검**
   - 원래 배치(k=0)의 개발 조건 08-11/1300/42에서 P0·M4를 돌린다. 이전 기준값과 소수점 끝까지 같아야 한다(NIGHT 재현 점검과 같은 방식).
   - W4는 FIXED24의 한 상황에서 결정 기록이 같아야 한다.
   - 하나라도 다르면 멈춘다.
2. **기준선**
   - 84상황 × P0·M4·W4 = 252회.
   - 회당 약 110초(FIXED24 실측)이므로 약 7.7 CPU-시간, 8 CPU에서 약 1시간이다.
   - 심판 감도 확인(M4 대 P0)도 여기서 나온다.
3. **B′ 관문 평가**
   - 84상황 × B′.
   - 에피소드당 롤아웃은 약 380개다(선택 지점 약 20 × 후보 약 2.4 × 미래 8). 롤아웃 1건이 약 13초(M4PROBE 실측)이므로 에피소드당 약 1.4~1.6 CPU-시간이다.
   - 합계 약 125 CPU-시간(선택 지점 수에 따라 80~190)이고, 8 CPU에서 약 16시간이다.
   - B가 끝나면 남은 상황을 B 런타임에 나눠 줄 수 있다. 이때 결과 폴더는 `referee/bprime_B`로 따로 둔다.

**관문 1 (사전 고정)**
- B′의 M4 대비 주 지표 점추정이 +0.3초 이상이면 2단계(Claude·Gemini 학습기)로 간다.
- 관문은 다음 일을 할지 정할 뿐이다. 성과로 주장하려면 2.4절의 통과 조건을 모두 채워야 한다.
- 점추정이 +0.3초 미만이면 두 학습기를 보류한다. 그다음은 행동 범위 넓히기, 즉 다른 종류의 조절 손잡이를 고정값으로 훑는 일이다.
- G1은 관문 결과와 무관하게 끝까지 간다.

### 런타임 B — B′ 자료 수집 (공통 기반)

**B′ 규칙 (사전 고정)**
- 기본은 M4다. 선택 지점마다 상태를 저장한다.
- 후보 녹색마다 표본 미래 8개로 롤아웃한다.
  - 첫 5초는 후보 녹색, 그 뒤 295초는 M4로 진행한다.
  - 비용은 300초 지연 + 남은 정체 × 75초다.
  - 표본 미래는 실제 미래 차를 지우고 최근 900초 차량에서 다시 뽑는다. 기존 장치를 그대로 쓴다.
  - 후보끼리 같은 미래 번호를 써서 짝으로 비교한다.
  - 미래 난수는 `sha256("ARENA3|BPRIME|<상태 이름>|<번호>")`로 정한다.
- 결정: M4가 아닌 후보 a의 짝 이득 평균 g_a가 0보다 크고, g_a ≥ 1.0 × 표준오차이면 a로 바꾼다. 그런 후보가 여럿이면 g_a가 가장 큰 것을 고른다. 없으면 M4를 따른다.
- 롤아웃 안의 후속 정책은 언제나 M4다. B′를 다시 부르지 않는 한 단계 롤아웃이다.
- 복원에는 M4PROBE의 진입 대기 보완을 쓴다(200·203절, 실제 SUMO에서 2/2 검증).

**B′ 점검 (실행 전)**
- **저장이 본 실행을 바꾸지 않는지:** B′ 장치로 상태를 저장하고 롤아웃까지 하되 항상 M4를 고르는 실행이 일반 M4 실행과 지표·결정 기록까지 같아야 한다(2상황).
- **복원 정확도:** 선택 지점마다 5초 재생 지문을 대조하고 일치율을 기록한다.
  - 본 실행의 성적은 끊김 없는 원래 시뮬레이션에서 재므로, 롤아웃 복원이 조금 어긋나도 판정 지표는 오염되지 않는다. 어긋남은 B′의 판단만 흐리게 한다.
  - 일치율이 95% 미만이면 멈추고 보고한다.

**수집 범위**
- 학습 8일 × 날짜마다 시간대 8개 × 배치 1개 = **64에피소드**.
- 시간대는 06:00~21:45의 15분 칸에서 해시로 뽑는다(날짜마다 겹치지 않게). 배치는 `T1~T64`.
- 약 95 CPU-시간(60~140), 8 CPU에서 약 12시간이다.
- 선택 지점은 약 1,300개로 예상된다. M4PROBE 31개의 40배 이상이다.

**저장 자료 (Claude·Gemini 학습기가 쓸 형식)**
- 선택 지점마다 남기는 것:
  - 공통 관측 119칸, 허용 녹색, 6개 모드의 첫 녹색, M4·P0·B′ 행동, 시각, 날짜·시간대·배치
  - 후보 × 미래마다 롤아웃 결과: 총비용, 동쪽·남쪽 좌회전 지연, 남은 정체, 규칙이 바꾼 횟수, 엿봄 수(0이어야 함)
- 기존 DelayMeter는 전체 지연만 세므로, 이동별로 나눠 세는 하위 클래스를 새로 만든다. 이것이 Gemini 학습기의 좌회전 헤드가 쓸 값이다.
- 에피소드 실제 성적(차량별 지연)도 함께 남긴다.
- 상태 파일은 용량 때문에 10%만 보관한다(해시로 고름).

### 런타임 C — GPT 학습기 G1

**N3와 무엇이 다른가 (먼저 확인한 사실)**
- GPT가 지적한 대로 WEIGHT1 기본 학습기는 탐험률을 전체 5초 단계로 줄이고 재생 자료를 고르게 뽑는다(`explore_weight_train.py:52`).
- 하지만 밤샘 N3(`explore_night_train.py`)가 이미 일부를 바꿨다. 묶음의 25%를 선택 지점에서 뽑았고, 탐험률은 0.5 → 0.2(바닥 유지)였으며, M4에서 출발했다. 결과는 M4 수준(+0.05초)이었다.
- 그래서 G1은 N3를 반복하지 않고 **선택 지점끼리만 잇는 학습(SMDP)**으로 한 걸음 더 간다.

| 항목 | N3 | G1 |
|---|---|---|
| 학습 단위 | 5초 단계, 10단계 묶음 | **선택 지점 → 다음 선택 지점** |
| 재생 자료 | 선택 지점 25% + 전체 75% | **선택 지점만 100%** |
| 할인 | 5초당 0.99 | 5초당 0.99, 지점 사이 경과 시간만큼(0.99^(Δt/5)) |
| 보상 | 실제 지연 증가(정확 정산) | 같음. 지점 사이 지연을 모두 합산, 꼬리는 마지막 전이에 접음 |
| 탐험률 | 단계 수 기준 0.5→0.2 | **선택 결정 수 기준** 0.5→0.1(첫 3,000번), 이후 0.1 |
| 모드 | 5개 | 6개(W4 포함, 공통 규칙) |
| 관측 | 110칸 | 공통 119칸 |
| 출발점 | M4(듀얼링, 이점 0 초기화) | 같음 |
| 기타 | — | 3단계 묶음, 새 전이 하나당 경사 8번, 목표망 1,250번마다 교체 |

**학습 상황과 예산**
- 학습 상황: 학습 8일 × 06:00~21:45의 무작위 15분 칸 × 에피소드마다 새 배치(`T1000+`).
- 학습 난수는 3개(42·43·44)다.
- 예산은 60 CPU-시간이다. 에피소드당 약 2분(WEIGHT1 실측)이므로 약 1,800에피소드, 난수당 약 600에피소드다. WEIGHT1_LONG의 417에피소드보다 많다.
- 학습 곡선용으로 난수마다 20만·40만 단계 시점의 모델도 저장한다. 공식 평가는 마지막 모델만 한다.

**평가**
- 학습이 끝나면 모델 3개 × 84상황 = 252회를 심판 코드로 평가한다(약 8 CPU-시간).
- 결과는 `referee/G1/`에 쓴다.

## 4. 실행 전 점검 (런타임별, 하나라도 실패하면 멈춤)

| 점검 | 통과 조건 |
|---|---|
| 도착 배치 바꾸기 | k=0 → 원래 파일 SHA, E·C·T 배치 → 서로 다른 SHA, 환경 지문 `b20888514ea3` 유지 |
| 잠금 대조 | 상황 84개의 차량 파일 SHA가 잠금 설정과 같음 |
| 심판 재현 | 08-11/1300/42에서 P0·M4 이전 값과 같음, W4 결정 기록 같음 |
| 6모드 계획기 | 모드 0~4의 첫 녹색이 WEIGHT1 계획기와 같음(기록된 상태로 비교) |
| B′ 무변경 | 항상 M4를 고르는 B′ 실행 = 일반 M4 실행 |
| B′ 엿봄 | 롤아웃 안에서 실제 미래 차가 지나간 수 0 |
| G1 전이 | 선택 지점 사이 보상 합 = 에피소드 정확 정산 합(허용 1e-6) |
| 시험 | 새 시험 + 기존 WEIGHT1·NIGHT·M4PROBE 시험이 모두 통과(가짜 SUMO) |

## 5. 결과 읽는 법

| B′ (관문 1) | 학습기 | 뜻 | 다음 |
|---|---|---|---|
| +0.3초 이상 | 하나 이상 통과 | RL이 M4 위 이득을 배움 | 승자를 C1·C2에서 확인 → 보고 |
| +0.3초 이상 | 모두 미통과 | 여지는 보이나 학습이 못 옮김 | 라벨 잡음·관측·상태 분포 점검 |
| +0.3초 미만 | G1만 진행 | 이 행동 범위에서 여지가 안 보임 | 다른 종류의 조절 손잡이 시험 |

- G1이 통과하면 "교사 없이 선택 지점 학습만으로 M4를 넘었다"는 별도 결론이 된다.
- B′의 결과와 상관없이 성립한다.

## 6. 한계 (결과 해석에 반드시 함께 적는다)

- 날짜는 15일 안에서만 나눴다. 평가 7일은 프로젝트에서 반복 사용한 날짜이므로 **반복 사용 날짜의 개발 비교**이고, 새 날짜나 실제 도로 일반화가 아니다.
- 날짜 7개의 t구간은 자유도가 6이라, 0.3초 안팎의 차이는 놓칠 수 있다. 미통과는 '여지 없음'의 증명이 아니다.
- 300초 대리 비용은 B′가 판단할 때만 쓴다. 판정은 60분 실제 지연으로만 한다.
- 6모드 행동 범위는 가중치 손잡이 하나뿐이다. 다른 종류의 행동은 시험하지 않는다.
