### 3.2 focused_scenario.py — 같은 수요와 실제 신호를 만든다

세 덩어리다. (A) 차량 파일, (B) 실제 신호 복원, (C) DQN·감응식용 신호 틀.

**(A) 차량 파일**

| 볼 곳 | 내용 |
|---|---|
| [151 `write_routes`](../src/focused_scenario.py#L151) | 15분 기록을 차량으로 바꾼다. 기록 1건 = 차 1대 |
| [194–199](../src/focused_scenario.py#L194) | 정지선 도착 시각을 15분 안에서 무작위로 뽑는다(`ARRIVAL_WINDOW_S` = 900, [34](../src/focused_scenario.py#L34)) |
| [217–218](../src/focused_scenario.py#L217) | 출발 시각 = 도착 시각 − 정지선까지 자유 주행 시간 |
| [86 `_chain`](../src/focused_scenario.py#L86), [110 `route_for`](../src/focused_scenario.py#L110) | 경로 = 상류 직진 구간 → 진입 → 진출 → 하류. 다음 신호 앞, 또는 차로가 절반 밑으로 줄기 전에 끊는다 |
| [40](../src/focused_scenario.py#L40), [128](../src/focused_scenario.py#L128), [200–210](../src/focused_scenario.py#L200) | 서쪽 접근로는 두 갈래(약 46% : 54%). 상류 기록 비율대로 나눈다 |
| [237 `route_seed`](../src/focused_scenario.py#L237) | 난수 = 날짜·시각으로 고정. 어느 실험에서든 같은 시간대는 같은 차가 나온다 |
| [289 `day_route_file`](../src/focused_scenario.py#L289) | 하루 차량 파일(환경 지문별로 따로 저장) |
| [47](../src/focused_scenario.py#L47) | 운전자 설정(`config/driver_model.json`)을 모든 차종에 붙인다 |

왜 이렇게 썼나:
- **도착을 15분 안에서 무작위로**: 1분 기록에는 실제 신호의 녹색 시점이 찍혀 있다(녹색이 없는 분은 2대, 녹색이 40초 넘는 분은 40대). 1분 단위로 도착시키면 차가 실제 신호의 녹색에 맞춰 와서 고정신호에 유리해진다. 대신 실제보다 도착이 덜 고르다. 이것이 동쪽 무리 도착 민감도를 두는 이유다.
- **주변 도로에서만 달리게**: 경로가 다른 신호를 지나면 그 신호의 영향이 섞인다. 차로가 크게 줄어드는 곳까지 끌고 가면 현실에 없는 병목이 생긴다.
- **서쪽 두 갈래**: 한 갈래로 몰아넣었더니 없는 병목이 생겨 직진이 자주 막혔다(직진 붕괴 12번 중 10번). 두 갈래로 나누자 0번이 됐다.

왜 이렇게 썼나:
- 파일을 그냥 이어 붙이면 경계마다 녹색이 잘리거나 빠진다. 예전 방식(v3.2)의 결함이었다. 고치자 고정신호 지연이 52.4초에서 50.4초로 바뀌었다.
- 원본 상태를 그대로 쓰면 관측 교통량을 처리할 수 없는 시간대가 대부분이었다. 그래서 1분 통과량과 녹색 시간의 관계로 '한 현시 밀림'을 확인하고 보정했다(근거: `docs/가상도로_정상화_20261004.md`).
- 손본 곳은 숨기지 않는다. 손본 시간대는 '불확실'로 표시하고, 결과도 그 시간대를 뺀 값을 따로 낸다.

### 3.3 focused_sumo.py — 모든 정책을 같은 틀로 돌린다

| 볼 곳 | 내용 |
|---|---|
| [38 `make_environment`](../src/focused_sumo.py#L38) | SUMO-RL 환경 하나로 세 정책을 모두 돌린다(`fixed_ts`가 참이면 고정·감응식, 거짓이면 DQN) |
| [114–121](../src/focused_sumo.py#L114) | 5초마다 판단, 순간이동 끔, 진입 못 한 차 버리지 않음, 충돌 검사 옵션 |
| [62–76](../src/focused_sumo.py#L62) | 대기열이 있는 상태에서 시작: 실제 신호로 1초씩 돌린 뒤 녹색이 막 켜진 순간에 넘긴다 |
| [78–111](../src/focused_sumo.py#L78) | 평가용: 매초 대기열·진입 대기·신호 상태 기록(SUMO '구독'으로 빠르게) |
| [31–35](../src/focused_sumo.py#L31) | 충돌 검사(교차로 안까지). `warn`을 쓰는 이유 |
| [140](../src/focused_sumo.py#L140), [154](../src/focused_sumo.py#L154), [172](../src/focused_sumo.py#L172) | 결과 파일 읽기(충돌 기록 파일이 없으면 멈춤) |

왜 이렇게 썼나:
- **순간이동 끔**: SUMO는 기본적으로 오래 막힌 차를 앞으로 옮겨 버린다. 그러면 정체가 가려진다.
- **진입 못 한 차를 버리지 않음**: 길이 꽉 차 들어오지 못한 차도 기다린 시간을 지연에 넣는다.
- **충돌은 `warn`**: 기본값(옮기기)이나 지우기를 쓰면 부딪힌 차가 사라져 정책마다 교통이 달라진다. 충돌을 낸 정책의 정체가 오히려 줄어들기도 한다. 그래서 차는 그대로 두고 충돌 기록을 따로 판정한다.

| 횡단보도 2개의 보행 대기 | 2 |
| 그대로 실행될 행동 표시 | 4 |

- 감지 구간([85 `build_zones`](../src/focused_rl.py#L85)): 이 지도는 교차로 앞 도로가 11~19m로 잘게 나뉘어 있다. SUMO-RL 기본 관측은 정지선 앞 2~3대만 본다. 그래서 상류 최대 300m까지 보고, 서쪽은 두 갈래를 모두 본다.

**점수(보상)** ([168](../src/focused_rl.py#L168)): −0.1 × (감지 구간에서 멈춘 차 + 도로에 못 들어온 차)

- 5초마다 바로 셀 수 있다. 멈춘 차 수를 시간에 걸쳐 더하면 총 대기와 비례한다.
- 약점: 차 수의 합만 보므로, 차가 적은 방향(예: 좌회전)을 오래 세워도 점수 손해가 작다. 그래서 아래 규칙 ④를 둔다.

**운영 규칙** ([182 `SignalConstraints`](../src/focused_rl.py#L182), 판단은 [324 `_decide`](../src/focused_rl.py#L324))

| 규칙 | 값 | 근거 |
|---|---|---|
| ① 최소 녹색 | 보행 현시 46·33초, 그 밖 15초 | 보행 진입 7초 + 횡단 길이 ÷ 1m/s([43–59](../src/focused_rl.py#L43), [74](../src/focused_rl.py#L74)) |
| ② 보행자 최대 대기 | 155·120초 | 실제 운영 신호의 99% 값을 5초 단위로 올림 |
| ③ 최대 녹색 | 120초 | 실제 녹색 최대는 106초라 DQN을 불리하게 묶지 않음 |
| ④ 차량 최대 누적 대기 | 165초 | 실제 운영 신호 15일, 148만 8,848대의 99% 값(`config/vehicle_wait_rule.json`) |

- 왜: 실제 신호도 지키는 규칙이다. DQN에만 특혜를 주지 않으려고 같은 기준을 씌운다. 기준값을 실제 신호의 99% 값으로 잡아 "실제보다 더 오래 세우지 않는다"를 지킨다.
- ④는 좌회전에 대해 실제 신호보다 엄격하다(실제 좌회전의 99% 값은 4~11분). DQN에 불리한 쪽이라 결론을 부풀리지 않는다. 민감도에서 완화도 본다.

**그대로 실행될 행동 표시** ([361 `allowed`](../src/focused_rl.py#L361)): 규칙을 씌워도 바뀌지 않는 행동이다. 관측 끝 4칸에 1/0으로 넣는다.

**학습기 `HoldAwareDQN`** ([438](../src/focused_rl.py#L438)). SB3의 DQN을 세 군데만 고쳤다.

| 고친 곳 | 내용 | 왜 |
|---|---|---|
| [443 `predict`](../src/focused_rl.py#L443), [457 `_sample_action`](../src/focused_rl.py#L457) | 실행 가능 표시 안에서만 고른다(탐험·학습 전 무작위도) | 고른 신호가 그대로 켜져야 배운 판단이 실행된다. 전에는 300번 중 6번 어긋났다 → 0번 |
| [464 `_store_transition`](../src/focused_rl.py#L464) | 실제로 켜진 현시를 기억한다 | 규칙이 바꾼 행동을 '고른 행동'으로 기억하면 행동과 결과가 어긋난다(v3 첫 학습: 판단의 85%가 무시됨) |
| [470](../src/focused_rl.py#L470), [477](../src/focused_rl.py#L477) | 미래 가치도 표시 안에서만 계산 | 실행할 수 없는 행동의 엉터리 값을 배우지 않게 |

**설명할 때 한마디**: "DQN은 5초마다 녹색 4개 중 하나를 고르는데, 규칙상 그대로 켜질 수 있는 것 중에서만 고릅니다. 규칙은 실제 신호에서 나온 숫자라서 DQN에게만 유리하거나 불리하지 않게 했습니다."

### 3.6-2 단순 제어 — "꼭 학습이 필요했나?"에 답하는 비교 (10-06 추가)

| 볼 곳 | 내용 |
|---|---|
| [159 `QueueFirst`](../src/focused_eval.py#L159) | 학습 없는 제어. 5초마다 규칙상 켤 수 있는 녹색 가운데, 그 녹색이 통과시키는 방향에서 기다리는 차가 가장 많은 녹색을 켠다 |
| [182 `waiting`](../src/focused_eval.py#L182) | 기다리는 차 = 감지 구간에서 멈춘 차(초속 0.1m 미만) + 도로에 못 들어온 차. DQN 점수와 같은 범위의 같은 차. 다만 차마다 어느 방향으로 갈지를 차의 경로로 안다([175 `movements`](../src/focused_eval.py#L175)). DQN은 이것을 모른다 |
| [192](../src/focused_eval.py#L192) | 같으면 지금 녹색 유지, 그다음은 번호가 작은 녹색. 조정할 숫자가 없다 |
| [276–279](../src/focused_eval.py#L276), [290](../src/focused_eval.py#L290) | DQN과 같은 운영 규칙(SignalConstraints)을 씌우고, 같은 틀 지도에서 돈다 |

왜 이렇게 썼나:
- DQN의 개선은 "규칙 안에서 상황을 보고 고르는 것"에서 올 수도 있고, "학습"에서 올 수도 있다. 같은 규칙·같은 정보로 학습 없이 고르는 제어와 비교해야 학습이 보탠 몫이 드러난다.
- **(10-07 바로잡음)** 지금 단순 제어는 규칙과 감지 범위만 같고, 정보는 같지 않다.
  - 단순 제어는 상류에 멈춘 차 10대가 "좌회전 9대, 직진 1대"인지까지 안다.
  - DQN은 진입로별 합계와 정지선 앞 차로(차로마다 1~3대)만 본다.
  - DQN 관측이 완전히 같은 두 상황에서 단순 제어가 다른 녹색을 고르는 것을 실제 코드로 확인했다.
  - 그래서 지금 비교로 말할 수 있는 것은 "회전 계획을 아는 단순 제어가 DQN보다 좋았다"까지다. 학습의 몫을 가르려면 DQN과 같은 정보만 쓰는 단순 제어가 따로 있어야 한다.
- 감응식은 정해진 순서대로만 돌아 이 질문에 답하지 못한다.
- 숫자를 하나도 조정하지 않는다. 검증 날짜에 맞춰 손보면 공정한 기준이 아니게 된다.

## 4. 실행 흐름 따라가기

### 4.1 DQN 평가 하루

1. `run` → `planned_runs`: 모델 파일 지문으로 결과 폴더를 정하고, 이미 있으면 건너뛴다([211](../src/focused_eval.py#L211)).
2. `run_day` → `day_route_file`: 그날 하루 차량 파일을 만든다. 모든 정책이 같은 파일을 쓴다([289](../src/focused_scenario.py#L289)).
3. `make_environment`: DQN용 틀 지도, 매초 기록 환경을 만든다([38](../src/focused_sumo.py#L38)).
4. `SignalConstraints.bind`: 운영 규칙을 붙인다([275](../src/focused_eval.py#L275)).
5. 5초마다 다음을 되풀이한다([288](../src/focused_eval.py#L288)).
   - 관측(실행 가능 표시 포함)
   - `predict`가 표시 안에서 Q 최댓값을 고름
   - 규칙 확인(바꿀 일이 없어야 함)
   - SUMO가 5초 진행
6. 끝나면 지연·오래 기다린 차·보행·충돌을 계산하고 `metrics.json`을 쓴다([320](../src/focused_eval.py#L320)).

### 4.2 학습 에피소드 하나

1. `reset` → `warm_start`: 학습 날짜의 시각 P를 고르고, 90분 차량 파일과 P−30분부터의 실제 신호를 준비한다([50](../src/focused_train.py#L50)).
2. `FocusedEnvironment.reset`: 실제 신호로 30분 남짓 1초씩 돌려 대기열을 만들고, 녹색 시작에 넘긴다([62](../src/focused_sumo.py#L62)).
3. 60분 동안 720번 판단하며 다음을 되풀이한다.
   - `_sample_action`·`predict`로 고르기(표시 안에서)
   - `step`: 규칙 → 5초 → 실제 켜진 현시
   - `_store_transition`: 실제 현시를 기억
   - `train`: 미래 가치도 표시 안에서 계산
4. 10,000단계마다 체크포인트를 저장한다.

### 4.3 가상 도로 점검 하루

`check_day` → 실제 신호 프로그램(`aihub_signal_program`) + 하루 차량 파일 → SUMO 하루 → `analyse`(GEH·밀린 대수·지연) → `judge_collisions` → `ACCEPTANCE`로 통과 여부를 판정한다.

   - 서쪽 두 갈래
   - 운전자 무작위 감속

   그 뒤 실제 신호로 15일이 모두 통과했다.
3. **범위를 줄였다.** 12개 교차로 대신 석천사거리 하나로 네 원칙을 먼저 갖췄다. 12개는 포기가 아니라 보류다.
4. **전체를 점검하고 정리했다.** 쓰지 않는 코드·자료를 보관 폴더로 옮겼다(코드 34개 → 9개, 10-06 민감도 파일 1개 추가로 지금 10개). 결함 7건을 고치고 결정 4가지를 반영했다(v5).
5. **외부 검토를 두 번 받아 잠갔다.** 충돌 기준을 확인된 것만 예외로 좁혔다. 평가 장부(모델 지문, 빠진 평가 거부)와 행동 선택(실행 가능한 것 안에서)도 고쳤다. 모두 재현해서 고치고 검사로 막아 둔 뒤 환경을 잠갔다.

## 6. 예상 질문과 답

**Q1. 왜 SUMO인가?**
교통 연구에서 널리 쓰는 공개 미시 시뮬레이터라 차 한 대씩 움직임을 계산한다. AI Hub 지도가 SUMO 형식으로 제공된다. 강화학습 연결 도구(SUMO-RL)도 있다.

**Q2. 왜 DQN인가?**
행동이 "녹색 4개 중 무엇을 켤까"로 개수가 정해져 있다. 상태는 숫자 64개다. 이런 문제에 쓰는 대표적인 강화학습이다. 검증된 구현(Stable-Baselines3)을 쓰고, 운영 규칙과 맞추기 위해 세 군데만 고쳤다.

**Q3. 실제 도로에서도 DQN이 낫다고 말할 수 있나?**
아니다. "이 가상 도로에서 같은 수요·운전자로 신호만 바꾸면"까지만 말한다. 실제 대기 시간 자료가 없어 지연의 절대값은 검증할 수 없다.

**Q4. 신호 자료를 손봤는데 조작 아닌가?**
손본 것은 기록 형식의 문제뿐이다(파일 경계, 기록 누락, 한 현시 밀림). 근거를 문서로 남겼다. 손본 시간대는 '불확실'로 표시하고, 그 시간대를 뺀 결과도 따로 낸다. 교통량은 손대지 않았다(1건 = 1대).

**Q5. 왜 도착 시각을 무작위로 뽑나?**
1분 기록에는 실제 신호의 녹색 시점이 찍혀 있다. 그대로 쓰면 고정신호에 유리하다. 대신 실제보다 도착이 덜 고르다. 그래서 민감도에서 동쪽 무리 도착을 꼭 확인한다.

**Q6. 운전자 무작위 감속을 왜 0으로 했나?**
SUMO 기본값(0.5)으로는 실제 신호로도 실제로 지나간 양을 따라가지 못했다. 학습·검증 날짜만으로 정했다. 0일 때 처리 능력이 교과서 범위(차로당 시간당 약 1,880대)다. 0.2도 민감도로 본다.

**Q7. 규칙이 DQN을 묶어 불공정하지 않나?**
실제 신호도 지키는 규칙이고, 기준값은 실제 운영 신호의 99% 값이다. 165초 규칙은 좌회전에 대해 실제보다 엄격하다. DQN에 불리한 쪽이라 결론을 부풀리지 않는다. 민감도에서 완화도 본다.

**Q8. 보상이 왜 지연이 아니라 멈춘 차 수인가?**
5초마다 바로 셀 수 있고, 시간에 걸쳐 더하면 총 대기와 비례한다. 진입 대기 차도 넣어 짧은 접근로가 넘치는 것을 DQN이 알게 했다. 적은 방향을 희생하는 약점은 규칙 ④로 막는다.

**Q9. 감응식은 왜 넣었나?**
DQN이 이겨야 할 더 강한 비교 기준이다. 실제 운영 방식은 아니라서 '참고'로 둔다. 보행 특혜가 없도록 최대 녹색을 맞췄다.

**Q10. 왜 하루를 끊지 않고 평가하나?**
15분마다 빈 도로에서 시작하면 앞 시간대의 대기열이 사라져 혼잡이 작게 보이고, 교착이 숨는다.

**Q11. seed는 어떻게 쓰나?**
- 학습 seed 5개: 학습마다 결과가 흔들리므로 5개를 따로 학습해 평균 ± 표준편차로 보고한다.
- 평가 seed 42: 모든 정책이 같은 값을 써서 같은 조건으로 비교한다.

**Q12. 시험 날짜는 어떻게 지키나?**
날짜 단위로 학습 13, 검증 2, 시험 4일로 나눴다(`config/focused_split.json`). 학습 코드는 학습 날짜만 읽는다. 시험 4일은 설정을 모두 정한 뒤 마지막에 한 번만 쓴다.

**Q13. 충돌은 어떻게 다루나?**
모든 실행에서 교차로 안까지 검사하고, 어디서 나든 센다. 원인을 재현으로 확인한 지도 오류 1종만 따로 센다. 이 오류는 서쪽 상류 분기점에서 차로가 8m 안에 3.2m 갈라지는 곳이다. 확인 안 된 충돌이 있으면 그 결과로 결론을 내지 않는다.

**Q14. 결과를 다시 만들 수 있나?**
있다. 그 근거는 다음과 같다.
- 원본을 그대로 보관하고 CRC로 검사한다.
- 난수를 날짜·시각으로 고정한다.
- 환경 지문을 쓴다.
- 맥과 Colab에서 같은 결과가 나오는 것을 확인했다.
- 자동 검사 28개가 있다.

**Q15. 왜 교차로 12개가 아니라 1개인가?**
자료가 교차로별 장부라 차를 이어 추적할 수 없다. 나머지 11곳의 신호 해석과 경로 추정도 남아 있다. 질문에 필요한 네 원칙을 한 곳에서 먼저 갖췄고, 12개는 보류했다.

**Q16. 외부 검토로 무엇이 바뀌었나?**
세 가지다.
- 충돌 기준: 넓은 면제 → 확인된 것만 예외
- 평가 장부: 모델 지문, 빠진 평가 거부
- 행동 선택: 실행 가능한 것 안에서

모두 재현하고 고쳤고, 자동 검사로 다시 생기지 않게 막았다.

**Q17. 동쪽 이웃 신호 민감도는 왜 중요한가?**
동쪽 이웃 신호(204822)는 석천사거리와 박자를 맞춰 돈다(97%). 그래서 실제로는 동쪽 차가 무리 지어 온다. 지금 가상 도로는 무작위로 도착시키므로 고정신호가 불리할 수 있다. 무리 도착으로 바꿔도 결론이 유지되는지 꼭 확인한다(만든 방법은 3.6-3).

**Q18. 학습 없는 단순 제어와는 왜 비교하나?**
DQN의 개선이 '학습' 덕인지, '규칙 안에서 상황을 보고 고르는 것' 덕인지 가르기 위해서다. 단순 제어는 기다리는 차가 가장 많은 녹색을 켜고, 조정할 숫자가 없다.

주의할 점(10-07 바로잡음): 지금 단순 제어는 DQN과 규칙은 같지만 정보가 다르다. 기다리는 차가 직진인지 좌회전인지 정확히 알고, DQN은 그것을 모른다. 그래서 지금 결과(단순 제어가 2~3초 더 짧음)로는 "회전 계획을 아는 단순 제어가 더 좋았다"까지만 말할 수 있다. 학습의 몫을 가르려면 DQN과 같은 정보만 쓰는 단순 제어와 비교해야 한다.

## 8. 용어 사전

| 용어 | 뜻 |
|---|---|
| 현시 | 신호 한 단계(어느 방향에 녹색을 주는지). DQN의 행동은 녹색 현시 4개 중 하나 |
| 황색 | 녹색에서 적색으로 바뀌기 전 4초 |
| 이동 | (들어온 도로 → 나간 도로) 한 쌍. 석천사거리에는 14개 |
| 감지 구간 | DQN이 차를 세는 범위. 정지선에서 상류 최대 300m |
| 진입 대기 | 출발 시각이 지났는데 길이 차서 도로에 못 들어온 차 |
| 지연 | 막힘 때문에 잃은 시간 + 진입 전 대기 |
| 누적 대기 | 진입 전 대기 + 도로에서 멈춰 있던 시간 합(움직여도 줄지 않음) |
| 환경 지문 / 평가 지문 | 조건 파일 내용으로 만든 12자리 이름. 바뀌면 다시 계산 |
| 에피소드 | 학습 한 판(준비 30분 + 제어 60분) |
| seed | 난수 시작값. 같으면 같은 결과 |
| Q값 | 그 행동을 했을 때 앞으로 받을 점수 합의 예측 |
| 탐험 | 학습 초반에 일부러 무작위로 골라 보는 것(20% 동안 1 → 0.05로 줄임) |
| 재생 버퍼 | 겪은 (상태, 행동, 점수, 다음 상태)를 모아 두고 섞어 배우는 저장소 |
| 목표망 | 학습을 안정시키려고 5,000단계마다만 바꾸는 Q값 계산용 사본 |
| GEH | 관측과 시뮬레이션 교통량의 차이를 재는 교통공학 지표. 5 미만이면 잘 맞음 |
| 불확실 시간대 | 신호 기록을 손본 15분 시간대. 결과를 포함·제외 두 가지로 낸다 |
| 감응식 | 차량 감지에 따라 녹색을 최소~최대 사이에서 늘리고 줄이는 신호 |
