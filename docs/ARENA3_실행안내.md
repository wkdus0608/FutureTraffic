## 실행 방법

1. 세 노트북을 각각 Colab에서 연다. 런타임은 모두 **CPU**(고용량 RAM 권장)로 고른다.
2. 각 노트북에서 **런타임 → 모두 실행**을 누르고 Drive 접근을 허용한다. 세 개를 동시에 돌려도 된다.
3. 각 노트북은 먼저 다음을 확인한다. 하나라도 실패하면 거기서 멈춘다.
   - 묶음 검사
   - 패키지 버전 확인(이전 실험과 같아야 함)
   - SUMO 없는 시험 28개
4. 중간에 끊기거나 멈추면 같은 노트북에서 **모두 실행**을 다시 누른다. 끝난 일은 해시를 확인한 뒤 건너뛰고, 학습은 마지막 체크포인트에서 이어진다.
5. 오류가 나면 셀 출력과 `arena3/logs/<A·B·C>/` 로그의 마지막 줄들을 보내 주면 된다.

## 런타임별 순서와 예상 시간 (CPU 8개 기준 추정)

### A 심판
1. 평가 84상황의 차량 파일 대조(1~3분, SUMO 없음)
2. **재현 점검**
   - 원래 차량(08-12 07:30, 난수 42)에서 P0·M4·W4의 평균 지연과 실행 신호가 FIXED24와 소수점까지 같아야 한다.
   - 다르면 멈춘다. 이때는 이후 결과를 이전 결과와 같은 장치로 볼 수 없다는 뜻이다.
3. 기준선: 84상황 × P0·M4·W4 = 252회(약 1시간)
4. B′ 관문 평가: 84상황(약 16시간, 10~24시간). 둘로 나눠 동시에 돈다.
5. 판정표(`arena3/referee/summary.md`)

### B B′ 자료
1. **실행 전 점검**(5~10분)
   - B′ 장치로 상태를 저장하고 롤아웃까지 하되 항상 M4를 고르는 실행이 일반 M4 실행과 지표·실행 신호까지 같아야 한다.
   - 처음 세 선택 지점의 '실제 미래 5초 재생'도 원래 실행과 같아야 한다.
   - 시간당 선택 지점 수와 롤아웃 1건 시간을 재서 에피소드당 비용을 추정한다(`smoke.json`).
2. 학습 날짜 64에피소드(약 12시간). 둘로 나눠 동시에 돈다.
3. 요약: 선택 지점 수, M4에서 바꾼 비율, 사용한 CPU-시간

### C G1
1. **실행 전 점검**: 진짜 SUMO로 한 묶음(에피소드 2개)을 점검용 폴더 `arena3/G1_smoke`에 학습한다(약 5분). 본 학습 폴더와 섞이지 않는다.
2. 학습: 난수 42·43·44를 동시에 돌린다(각각 에피소드 2개씩 병렬). 난수마다 20 CPU-시간에서 멈춘다(약 10시간).
3. 심판 평가: 모델 3개 × 84상황 = 252회(약 1시간) → 판정. 런타임 A의 기준선이 아직 없으면 판정은 건너뛰고, 나중에 A의 마지막 칸을 다시 돌리면 함께 판정된다.

## 판정 읽는 법 (잠금 설정 `judge`)

M4 대비 이득(초/대, +면 후보가 짧음)이다. 아래를 **모두** 만족해야 `pass`다.

- 날짜 7개 평균 ≥ +0.3초
- 날짜 t95 하한 > 0
- 양수 날짜 ≥ 5
- 좌회전 동·남 각각 M4 + 5초 이내
- 300초 초과 차량 수가 M4 이하
- 정책에만 나는 미확인 충돌 0, 품질 오류 0

판정 결과가 `hold_shared_collision`이면, M4·P0에도 같은 미확인 충돌이 있어서 재현 진단을 마치기 전까지 판정을 보류한다는 뜻이다.

표 아래의 '심판 감도 확인'은 같은 계산으로 본 M4 대 P0다. 이전 세 묶음에서 M4가 0.8~1.1초 짧았다. 여기서도 하한이 0보다 크지 않으면 '심판 감도 부족'으로 표시한다.

학습기(G1, 이후 Claude·Gemini)는 모델 3개의 평균으로 판정하고, 통과한 1등은 확인 배치(C1·C2)에서 한 번 더 잰다. B′는 탐색 제어라 강화학습 결과와 섞어 쓰지 않는다. 모든 결과는 반복 사용 날짜의 개발 비교이고, 새 날짜나 실제 도로 일반화가 아니다.
